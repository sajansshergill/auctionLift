# AuctionLift — Should Whatnot extend the auction timer when a bid lands in the final seconds?

An end-to-end product data science project: simulate live-commerce auction data, build it through a modern data stack, and run a marketplace-grade A/B test to answer one real question — **does an anti-sniping "soft close" timer actually grow GMV, or does it just slow the stream down?**

Built to mirror the day job of a Product Data Scientist on a live-shopping marketplace: KPI ownership, experiment design, causal inference, experiment-validity guardrails, and a stakeholder-ready recommendation.

**Headline finding:** soft close raises winning prices (+1.7% per auction, significant) but the longer auctions cut throughput by 6.3%, so **net GMV per stream falls 3.7%** — the intuitive "prices go up, ship it" read is a trap. The project detects that, decomposes it, and recommends against a global rollout.

---

## The problem

On a live-shopping platform, revenue is generated by auctions running inside a seller's stream. A recurring product question is what should happen when a bid arrives in the last few seconds of an auction:

- **Hard close** — the auction ends exactly on time. Fast and predictable, but rewards "sniping" (bidding at the last possible moment so nobody can respond).
- **Soft close** — a late bid extends the timer by a few seconds, giving other buyers a chance to respond.

The tradeoff is genuinely unclear, which is what makes it worth an experiment instead of an opinion:

- Soft close **may raise price per item** — more back-and-forth bidding pushes the winning price up.
- Soft close **may lower throughput** — auctions take longer, so fewer items sell per stream in a fixed-length stream.

Net effect on GMV is ambiguous a priori. That's the whole point.

Most experiment analyses skip these and quietly ship bad reads. The gate exits non-zero on failure, so it can run in CI.

## Approach

### 1. Simulate live-commerce event data — from a known ground truth
There's no public Whatnot dataset, so `data_gen/simulate.py` generates event-level logs with realistic structure: power-law seller sizes, sniping concentrated in the final seconds, a fixed per-stream time budget that creates the throughput constraint, and a pre-period GMV covariate for CUPED. Critically, the data is generated from a **planted treatment effect**, and the simulator prints that ground truth — so the analysis has a target to recover. If the pipeline can't recover the planted effect, the pipeline is wrong.

### 2. Build a modern data stack
Raw events → **dbt** staging views → **dbt** mart tables in **DuckDB**. DuckDB stands in for Snowflake/BigQuery locally; the SQL ports cleanly. `dbt build` also runs `unique` / `not_null` / `accepted_values` tests on the marts.

### 3. Define the KPI tree
The metrics I'd own and defend, organized so a PM can see how a local change rolls up to GMV:

- **North star:** GMV per stream
- **Price side:** average sale price, bids per auction
- **Throughput side:** items sold per stream, auction duration
- **Retention proxy:** pre-period GMV covariate (also the CUPED input)

### 4. Design and analyze the experiment
Built to signal *marketplace* experimentation specifically, not generic A/B testing:

- **Randomize by stream, not by bid or auction** — bids within a stream aren't independent, so the unit of randomization has to be the stream.
- **Stream-level decision metric (GMV/stream)** with **CUPED** using pre-period GMV, and HC-robust SEs.
- **Auction-level mechanism metric (price)** with **standard errors clustered by stream** — the statistically correct way to test a per-auction effect under stream-level assignment.
- **Decompose** the net GMV effect into a price component and a throughput component. That decomposition is the actual insight.
- **Power / MDE** (`analysis/power.py`) shows how much CUPED shrinks the sample needed.

### 5. Ship the readout
A **Streamlit dashboard** for the KPI tree and result, plus a **one-page memo** written for a PM: what we tested, the lift, the risk, and a clear ship / don't ship / iterate call.

## Results (seed 42, 2,000 streams)

```
DECISION METRIC — GMV per stream (CUPED-adjusted, HC-robust SE)
  lift:            -3.68%   95% CI [-5.30%, -2.07%]   p < 0.001
  CUPED cut SE^2 by 88.3%

MECHANISM — winning price per auction (clustered SE by stream)
  price lift:      +1.66%   95% CI [+0.90%, +2.41%]   p < 0.001

DECOMPOSITION
  price effect:      +1.66%   (blended across all auctions)
  throughput effect: -6.34%   (items sold per stream)
  net GMV/stream:    -3.68%

RECOMMENDATION: do not ship a global rollout; test on high-demand streams.
```

## Running it

```bash
pip install -r requirements.txt

# one command, end to end
./run.sh

# or step by step:
python -m data_gen.simulate --streams 2000 --seed 42   # -> auctionlift.duckdb + ground truth
DBT_PROFILES_DIR=. dbt build                           # build + test the warehouse
python -m analysis.validity                            # gate: must pass before trusting results
python -m analysis.power                                # sample size / MDE
python -m analysis.effect                               # the treatment-effect readout
streamlit run dashboard/app.py                          # dashboard

pytest -q                                               # data contracts + correctness tests
```

## What "done" looks like

- The analysis recovers the planted effect within its confidence interval.
- `dbt build` passes all schema tests.
- The validity gate passes on clean data and fails (non-zero exit) on corrupted data.
- The memo makes a defensible ship / no-ship call with the tradeoff stated plainly.

## Notes

Data is synthetic and generated for demonstration; no real platform data is used, and the repo claims no affiliation. The point isn't the specific number — it's the decision process a marketplace runs to get to a trustworthy one.
